Trust built into the pipeline, not bolted on

Every pipeline is signed, verified, and accountable before it runs.

FlowPilot is a lightweight ETL studio and runtime. Its security model answers one question end to end: can this runtime prove exactly what it is about to execute, and who authorised it? The chain below is enforced by default.

Enrolment is one-time and offline: only the developer's public key crosses the boundary.

What FlowPilot protects

Six capabilities, all implemented today. Each is grounded in standard, audited cryptography — nothing home-grown.

Integrity
& authenticity

Signed artifacts, verified execution

Compiling a pipeline produces a signed artifact. Before running, the runtime verifies the signature against a list of authorised keys, recomputes the plan's hash, and refuses anything unsigned, unauthorised, or altered. The runtime executes only pipelines it can prove are genuine and unmodified.

The signature covers the whole manifest — plan, monitor endpoint, log level, secret names, provenance — so tampering with any of them in transit breaks verification.

Ed25519SHA-256 canonical plan hashfail-closed
Key
protection

The developer's private key stays private

The signing key is encrypted at rest with a passphrase and never leaves the developer's machine. It is unlocked in memory for the working session only, and wiped from memory when locked or on exit. The runtime holds only public keys.

Argon2id derives the encryption key from the passphrase; XChaCha20-Poly1305 protects the key material; sensitive buffers are zeroised after use.

Argon2idXChaCha20-Poly1305zeroised memory
Secrets

Secrets never travel inside artifacts

Pipelines reference secrets by name. The actual values live only on the machine that runs the pipeline, resolved at execution time from environment variables or the OS keychain. An artifact you move between teams or environments carries the names of the secrets it needs, never the values.

env → OS keychainnames, not values
Attribution
& control

Every run is accountable, every key revocable

Each execution records which developer signed the artifact and the exact plan it ran. Authorising a new developer is a one-time entry in the runtime's trust store; removing a compromised or departed developer is a single change that takes effect on the next run. Multiple developers can sign independently — no shared keys.

per-signer auditinstant revocationmulti-developer allowlist
Desktop
hardening

The studio is a hardened surface

The studio's desktop application is locked down to the minimum it needs: a strict content-security policy stops any injected script from running, its process permissions are reduced to essentials, and all assets are bundled locally so it works fully offline with no external content. A build-time guard blocks the code patterns that would reopen these risks.

This closes the one path — a scripting injection in the interface — that could otherwise sidestep the signing and key protections above.

small surface

A lean core, by design

The runtime is a single self-contained binary in Rust — no application server, no Java runtime, no sprawling platform to secure and patch. A smaller footprint means fewer moving parts and a smaller attack surface, and it runs comfortably in restricted or air-gapped networks.

How verification works

Before a single row is processed, the runtime runs these checks in order. Any failure stops execution — it never falls through to a partial or unverified run.

  1. Signed envelope present. The artifact carries a manifest and a signature.
  2. Engine compatibility. The artifact declares a runtime it is compatible with.
  3. Authorised signer. The signing key is present and active in the runtime's trust store.
  4. Valid signature. Verified with the trusted public key — not with any key carried inside the artifact.
  5. Untampered plan. The plan's hash is recomputed and matched against the signed value.
  6. Policy. The pipeline is allowed to run on this runtime.
  7. Admit & execute. Only now does processing begin, with the verified signer recorded.

Three modes govern enforcement: enforce (reject anything that fails — recommended for production), warn (run but flag, for migration), and off (isolated development only). The default posture for release is enforce.

Security posture

An honest split between what is enforced today and what is on the near-term roadmap. We would rather be precise than expansive.

Guaranteed today

Implemented and enforced

  • Signed artifacts with fail-closed verificationauthenticity, integrity, authorisation
  • Private key encrypted at rest & wiped from memory
  • Secrets resolved on target, never in artifacts
  • Per-signer attribution & instant revocation
  • Hardened, offline-capable studio (strict CSP, least privilege)
  • Air-gap-friendly: no studio-to-runtime connection required

On the roadmap

Planned hardening

  • Encrypted transport & authentication for the monitoring service
  • Sandboxed, least-privilege runtime execution
  • Hardware-backed keys (HSM / OS secure enclave) option
  • Supply-chain integrity: signed binaries & dependency auditing
  • Secret redaction in logs & run records
  • Optional encryption of artifacts for confidentiality
What the model is, and isn't. FlowPilot guarantees that a runtime executes only pipelines produced by an authorised developer and untouched since signing, and that private keys are protected on disk and in memory. It does not, on its own, defend a developer's machine that is already compromised at the operating-system level — the defence there is hardware-backed keys and endpoint security, which we integrate with rather than replace. We state this plainly because a serious security review will, and we would rather have that conversation directly.
