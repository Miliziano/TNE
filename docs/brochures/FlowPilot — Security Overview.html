Trust built into the pipeline, not bolted on

Every pipeline is signed, verified, and accountable before it runs.

FlowPilot is a lightweight ETL studio and runtime. Its security model answers one question end to end: can this runtime prove exactly what it is about to execute, and who authorised it? The chain below is enforced by default.

Enrolment is one-time and offline: only the developer's public key crosses the boundary.

What FlowPilot protects

Eight capabilities, all implemented today. Each is grounded in standard, audited cryptography and libraries. Nothing is home-grown.

Integrity
& authenticity

Signed artifacts, verified execution

Compiling a pipeline produces a signed artifact. Before running, the runtime verifies the signature against a list of authorised keys, recomputes the plan's hash, and refuses anything unsigned, unauthorised, or altered. The runtime executes only pipelines it can prove are genuine and unmodified.

The signature covers the whole manifest: plan, monitor endpoint, log level, secret names and provenance. Tampering with any of them in transit breaks verification.

Key
protection

The developer's private key stays private

The signing key is encrypted at rest with a passphrase and never leaves the developer's machine. It is unlocked in memory for the working session only, and wiped from memory when locked or on exit. The runtime holds only public keys.

Argon2id derives the encryption key from the passphrase, with fixed parameters so that keys encrypted today stay readable after library upgrades. XChaCha20-Poly1305 protects the key material, and sensitive buffers are zeroised after use.

Argon2idXChaCha20-Poly1305zeroised memory
Secrets

Secrets never travel inside artifacts, and never reach the logs

Pipelines reference secrets by name. The actual values live only on the machine that runs the pipeline, resolved at execution time from environment variables or the OS keychain (macOS Keychain, Windows Credential Manager, Linux Secret Service). An artifact you move between teams or environments carries the names of the secrets it needs, never the values.

The runtime keeps a register of every secret value it has resolved and masks them as *** in node log messages and error reports before they are written or sent to the monitoring service. A command line or connection string that embeds a password does not leak through a failure message.

Masking applies to the literal value. Transformed forms, such as a URL-encoded password, are not recognised, and data rows written by the pipeline's own outputs are not altered.

env → OS keychainnames, not valuesredacted in logs & events
Attribution
& control

Every run is accountable, every key revocable

Each execution records which developer signed the artifact and the exact plan it ran. Authorising a new developer is a one-time entry in the runtime's trust store; removing a compromised or departed developer is a single change that takes effect on the next run. Multiple developers can sign independently, with no shared keys.

per-signer auditinstant revocationmulti-developer allowlist
Monitoring
service

The monitor is closed by default

The central monitoring service listens on the local interface only unless configured otherwise, and refuses to start without two separate access tokens: one for runtimes that send events, one for people and tools that read them. Sending and reading never share a credential.

Event ingestion rejects browser-originated requests, caps request size and per-address volume, and serves a bounded worker pool. Repeated failed logins block the address for reading. Every page is sent with a strict content-security policy and no external resources, and all event content is escaped before display.

local bind by defaultseparate ingest / read tokensrate & size limits
Connectors

Data leaves and arrives over protected channels

Connectors encrypt where the protocol allows it and say so when it does not. FTPS negotiates TLS before sending credentials, MQTT applies its TLS setting instead of ignoring it, and LDAP uses LDAPS with certificate verification by default and rejects empty passwords that would silently become anonymous binds. Statements the database output generates validate every table and column name before it reaches SQL, and pass values as bound parameters.

TLS before loginLDAPS + cert checksinjection-safe SQL identifiers
Desktop
hardening

The studio is a hardened surface

The studio's desktop application is locked down to the minimum it needs: a strict content-security policy stops any injected script from running, its process permissions are reduced to essentials, and all assets are bundled locally so it works fully offline with no external content. A build-time guard blocks the code patterns that would reopen these risks.

This closes the one path, a scripting injection in the interface, that could otherwise sidestep the signing and key protections above.

No JVM,
small surface

A lean core, by design

The runtime is a single self-contained binary in Rust, with no application server, no Java runtime and no sprawling platform to secure and patch. A smaller footprint means fewer moving parts and a smaller attack surface, and it runs comfortably in restricted or air-gapped networks.

The toolchain is pinned, and dependencies are kept current: known advisories against the database, FTP and spreadsheet libraries were closed by upgrading or replacing them.

How verification works

Before a single row is processed, the runtime runs these checks in order. Any failure stops execution. It never falls through to a partial or unverified run.

  1. Signed envelope present. The artifact carries a manifest and a signature.
  2. Engine compatibility. The artifact declares a runtime it is compatible with.
  3. Authorised signer. The signing key is present and active in the runtime's trust store.
  4. Valid signature. Verified with the trusted public key, never with a key carried inside the artifact.
  5. Untampered plan. The plan's hash is recomputed and matched against the signed value.
  6. Admit & execute. Only now does processing begin, with the verified signer recorded.

Verification cannot be switched off. There is no setting that skips or softens it, so a forgotten default or a development setting copied to production cannot disable it. Any failure, including a missing or unreadable trust store or one with unsafe file permissions, stops the run before it starts.

What the model is, and isn't. FlowPilot guarantees that a runtime executes only pipelines produced by an authorised developer and untouched since signing, and that private keys are protected on disk and in memory. Signing proves who authorised a pipeline, not that what it does is safe: a signed pipeline with a shell node runs that command. It also does not, on its own, defend a developer's machine that is already compromised at the operating-system level; the defence there is hardware-backed keys and endpoint security, which we integrate with rather than replace. We state this plainly because a serious security review will.
